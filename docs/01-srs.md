## 1. ภาพรวมระบบ

### 1.1 วัตถุประสงค์
สร้าง web application สำหรับรับแจ้งปัญหาและติดตามงาน support ของกลุ่มบริษัท AIDC 7 บริษัท ทดแทนการแจ้งผ่าน LINE/โทรศัพท์/อีเมลที่กระจัดกระจาย เพื่อให้ (1) ไม่มีเรื่องแจ้งตกหล่น (2) วัด SLA ได้ (3) มีคลังความรู้ให้ผู้ใช้แก้ปัญหาเบื้องต้นเอง

### 1.2 ขอบเขต (In scope — MVP เฟส 1)
| กลุ่มความสามารถ | สาระสำคัญ |
|---|---|
| Ticket + SLA + Assign | แจ้งปัญหา, จัดหมวดหมู่, กำหนดผู้รับผิดชอบ, ติดตามสถานะ, นับ SLA |
| Multi-company + สิทธิ์ | แยกข้อมูล 7 บริษัท, role-based access control, row-level scoping |
| Dashboard + รายงาน | สถิติตามบริษัท/ประเภท/ผู้รับผิดชอบ, export Excel/PDF |
| Knowledge Base + แจ้งเตือน | คลังบทความ, แจ้งเตือน Email และ LINE |

### 1.3 นอกขอบเขต (Out of scope เฟส 1)
Asset/inventory management, Change management (ITIL), Chat แบบ realtime, Mobile native app, SSO (ออกแบบเผื่อแต่ยังไม่ทำ), Customer portal สำหรับลูกค้าภายนอก, Auto-classify ด้วย AI, ระบบอนุมัติหลายชั้น (approval workflow)

## 3. บทบาทผู้ใช้ (User Roles)

| รหัส role | ชื่อไทย | ขอบเขตข้อมูล | ความสามารถหลัก |
|---|---|---|---|
| `end_user` | ผู้แจ้ง (พนักงานทั่วไป) | ticket ที่ตนสร้าง หรือถูกระบุเป็นผู้ร้องขอ | สร้าง/ดู/คอมเมนต์/แนบไฟล์/ปิดเรื่องของตน, อ่าน KB |
| `agent` | เจ้าหน้าที่ support | ticket ในบริษัทที่ตนถูกมอบหมาย (1 คนดูแลได้หลายบริษัท) | รับงาน, เปลี่ยนสถานะ/priority, assign ต่อ, ตอบภายใน/ภายนอก, เขียน KB |
| `company_admin` | ผู้ดูแลระดับบริษัท | ทุก ticket **ในบริษัทของตนเท่านั้น** | ทุกอย่างที่ agent ทำได้ + จัดการผู้ใช้/แผนก/หมวดหมู่ของบริษัทตน + ดู dashboard บริษัทตน |
| `super_admin` | ผู้ดูแลระบบส่วนกลาง | ทุกบริษัท | ตั้งค่าทั้งระบบ, SLA policy, business hours, role, ดู audit log |
| `manager_viewer` | ผู้บริหาร (อ่านอย่างเดียว) | ตามบริษัทที่ได้รับสิทธิ์ (1 หรือหลายบริษัท) | ดู dashboard/รายงาน/export เท่านั้น — แก้ไขอะไรไม่ได้ |

> รายละเอียดสิทธิ์ระดับการกระทำ ดู `04-rbac-sla.md` หัวข้อ 1

**ข้อกำหนดการมอบ role**
- ผู้ใช้ 1 คนมีได้หลาย role และผูกกับ **บริษัทหลัก 1 บริษัท** (`user.company_id`)
- role `agent` / `company_admin` / `manager_viewer` ผูกขอบเขตบริษัทเพิ่มเติมผ่านตาราง `user_role_scope` (ดู `02-data-model.md`)
- **[ต้องยืนยันกับ PM]** agent ส่วนกลางที่ดูแลทั้ง 7 บริษัทมีจริงหรือไม่ — เอกสารนี้สมมติว่า **มี** และรองรับด้วยการให้ scope หลายบริษัท

## 5. ข้อกำหนดที่ไม่ใช่เชิงหน้าที่ (Non-Functional Requirements)

### 5.1 Performance

| รหัส | ข้อกำหนด | เกณฑ์วัด |
|---|---|---|
| NFR-01 | เวลาตอบสนอง API ทั่วไป | p95 ≤ 500 ms (ไม่รวม export) |
| NFR-02 | โหลดหน้ารายการ ticket 50 รายการ | ≤ 2 วินาที บน 4G |
| NFR-03 | ขนาด JS bundle แรก | ≤ 300 KB (gzip) |
| NFR-04 | Export Excel 10,000 แถว | ≤ 30 วินาที (ทำเป็น background job ถ้าเกิน 5,000 แถว) |
| NFR-05 | รองรับผู้ใช้ใช้งานพร้อมกัน | 200 concurrent users |
| NFR-06 | ปริมาณข้อมูลที่ออกแบบรองรับ | ผู้ใช้ลงทะเบียน 3,000 คน, ticket 30,000 ใบ/ปี, ไฟล์แนบ 50 GB/ปี |

### 5.2 Security

| รหัส | ข้อกำหนด |
|---|---|
| NFR-10 | รหัสผ่านเข้ารหัสด้วย Argon2id; นโยบายรหัสผ่าน ≥ 8 ตัวอักษร มีตัวอักษรและตัวเลข |
| NFR-11 | JWT: access token 30 นาที, refresh token 7 วัน (เพิกถอนได้ผ่าน Redis blacklist) |
| NFR-12 | บังคับ HTTPS (TLS 1.2+); ใบรับรองภายในองค์กรได้ |
| NFR-13 | **Row-level scoping บังคับที่ชั้น query ของ backend เสมอ** ห้ามพึ่งการซ่อน UI เพียงอย่างเดียว |
| NFR-14 | ป้องกัน SQL injection ด้วย ORM/parameterized query เท่านั้น |

## 6. User Stories และ Acceptance Criteria

> รูปแบบ: **Given** (สถานการณ์ตั้งต้น) / **When** (การกระทำ) / **Then** (ผลที่คาดหวัง)

### US-01 แจ้งปัญหาจากมือถือหน้างาน `end_user` · MVP
**ในฐานะ** พนักงานหน้างานก่อสร้าง **ฉันต้องการ** แจ้งปัญหาพร้อมแนบรูปจากมือถือ **เพื่อ** ให้ทีม IT เห็นปัญหาโดยไม่ต้องอธิบายยาว

| AC | เกณฑ์ |
|---|---|
| AC-1 | **Given** ล็อกอินบนมือถือแล้ว **When** กด "แจ้งปัญหา" กรอกหัวข้อ+รายละเอียด เลือกหมวดหมู่ ความเร่งด่วน แล้วกดส่ง **Then** ระบบสร้าง ticket สถานะ `new` และแสดงเลขที่ ticket |
| AC-2 | **Given** อยู่หน้าสร้าง ticket **When** แนบรูปขนาด 8 MB **Then** ระบบบีบอัดฝั่ง client ให้ ≤ 2 MB ก่อนอัปโหลด และแสดง progress |
| AC-3 | **Given** ส่ง ticket สำเร็จ **When** ระบบบันทึกเสร็จ **Then** ผู้แจ้งได้รับการแจ้งเตือนยืนยันตามช่องทางที่เปิดไว้ ภายใน 1 นาที |
| AC-4 | **Given** กรอกไม่ครบฟิลด์บังคับ **When** กดส่ง **Then** ระบบแสดงข้อความภาษาไทยชี้ฟิลด์ที่ขาด และ**ไม่**ล้างข้อมูลที่กรอกไว้ |

| A-05 | **[ต้องยืนยันกับ PM]** LINE | ใช้ LINE Notify (บริการปิดตัวแล้วในหลายพื้นที่) — เอกสารออกแบบให้ `notification_channel` เป็น adapter เพื่อสลับไป LINE Messaging API (OA) ได้ | ถ้าใช้ LINE OA ต้องมีบัญชี OA + ค่าใช้จ่ายรายเดือน + ผู้ใช้ต้องเพิ่มเพื่อน |

| A-07 | **[ต้องยืนยันกับ PM]** แหล่งข้อมูลพนักงาน | นำเข้าครั้งแรกจาก Excel แล้วดูแลในระบบเอง | ถ้าต้อง sync กับ AD/HR system ต้องเพิ่มงาน integration (ประเมิน 5–8 วัน) |
| A-08 | **[ต้องยืนยันกับ PM]** ผู้แจ้งแทนผู้อื่น | agent สร้าง ticket แทนผู้ใช้ได้ (`requester_id` ≠ `created_by`) | โครงสร้างรองรับแล้ว |
| A-09 | **[ต้องยืนยันกับ PM]** การเก็บข้อมูลย้อนหลัง | เก็บ ticket ตลอดอายุระบบ ไม่มี archive policy ในเฟส 1 | ถ้าต้อง purge ตาม PDPA ต้องกำหนดนโยบายเก็บข้อมูล |

| A-11 | **[ต้องยืนยันกับ PM]** ความพร้อมโครงสร้างพื้นฐาน | มีเซิร์ฟเวอร์ในองค์กร 4 vCPU/8 GB/200 GB + Docker + สิทธิ์ผู้ดูแล | ถ้าไม่มี ต้องเผื่อเวลาจัดหา |
