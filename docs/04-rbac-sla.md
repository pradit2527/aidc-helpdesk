## 1. นิยาม Role และขอบเขตข้อมูล

| role | ชื่อไทย | ขอบเขตข้อมูล (row-level) | ตัวอย่างผู้ถือ role |
|---|---|---|---|
| `end_user` | ผู้แจ้ง | เฉพาะ ticket ที่ตนเป็น `requester_id` หรือ `created_by` | พนักงานทั่วไป, คนขับรถ, ช่างหน้างาน |
| `agent` | เจ้าหน้าที่ support | ทุก ticket ในบริษัทที่อยู่ใน `scoped_company_ids` | ทีม IT ส่วนกลาง, IT ประจำบริษัท |
| `company_admin` | ผู้ดูแลระดับบริษัท | ทุก ticket + ผู้ใช้ + การตั้งค่าย่อย ในบริษัทที่อยู่ใน `scoped_company_ids` | หัวหน้า IT ของแต่ละบริษัท |
| `manager_viewer` | ผู้บริหาร (อ่านอย่างเดียว) | อ่าน ticket/รายงาน ในบริษัทที่อยู่ใน `scoped_company_ids` | ผู้จัดการฝ่าย, ผู้บริหารกลุ่ม |
| `super_admin` | ผู้ดูแลระบบ | ทุกบริษัท ไม่มีข้อจำกัด | หัวหน้า IT กลุ่ม AIDC (แนะนำไม่เกิน 2 บัญชี) |

### 1.1 กติกาสำคัญ

1. ผู้ใช้ทุกคนมี `end_user` เป็นพื้นฐานเสมอ และเพิ่ม role อื่นได้
2. มีหลาย role → สิทธิ์คือ **ผลรวม (union)** ของ permission และ **ผลรวมของขอบเขตบริษัท**
3. `super_admin` ทับทุกกฎ — จำกัดจำนวนบัญชีและมี audit log ทุกการกระทำ
4. `manager_viewer` เป็น role อ่านอย่างเดียวโดยเจตนา: **การมี role อื่นควบคู่ไม่ทำให้เป็น read-only** — ถ้าต้องการให้ผู้บริหารแก้ไขไม่ได้ ต้องมอบเฉพาะ `end_user` + `manager_viewer`
5. ขอบเขตบริษัทมาจาก `user_role_scope` **ที่ยังไม่หมดอายุ** (`user_role.expires_at`) ถ้าไม่กำหนด → ใช้ `app_user.company_id`
6. **ทุกการตรวจสิทธิ์ต้องทำที่ backend** การซ่อนปุ่มใน UI เป็นเพียงประสบการณ์ผู้ใช้ ไม่ใช่มาตรการความปลอดภัย
7. **`approval.decide` ไม่ผูกกับ role** — มอบให้เฉพาะผู้ที่เป็น `approver_id` ของแถวนั้นเท่านั้น ผู้อนุมัติอาจเป็นหัวหน้าหน่วยงานที่ไม่ได้เป็น agent เลยก็ได้
8. **เหตุความปลอดภัย (`is_security_incident`) ใช้ขอบเขตแคบกว่าบริษัท** — ดูหัวข้อ 2.7

> ### 🔑 สัญญากับ Frontend
> เงื่อนไข **O** (เฉพาะของตน) และ **S** (เฉพาะบริษัทตน) ในเมทริกซ์นี้ **frontend ไม่ต้องคำนวณเอง** — `GET /tickets/{id}` คืนบล็อก **`can: {}`** ที่ backend ประเมินครบทุกเงื่อนไขแล้ว (ปิดประเด็น FE-02) หน้าที่ของ frontend คือซ่อน/แสดงตาม `can` เท่านั้น

### 2.2 การอนุมัติและ Checklist (4 permission) 🆕

| `permission code` | การกระทำ | end_user | agent | company_admin | manager_viewer | super_admin |
|---|---|---|---|---|---|---|
| **`approval.read`** | ดูขั้นการอนุมัติของ ticket | **O** | **S** | **S** | **S** | ✔ |
| **`approval.decide`** | อนุมัติ/ปฏิเสธ | **เฉพาะผู้ที่เป็น `approver_id` ของแถวนั้น — ไม่ผูกกับ role ใด ๆ** | | | | |
| **`approval.manage`** | เปลี่ยนผู้อนุมัติเมื่อหาคนไม่ได้ | ✘ | ✘ | **S** | ✘ | ✔ |
| **`checklist.update`** | ติ๊กรายการ checklist + แนบหลักฐาน | ✘ | **S** | **S** | ✘ | ✔ |

**กฎบังคับของ approval**
- ขั้น `n+1` เปิดใช้ได้เมื่อขั้น `n` เป็น `approved`
- **ห้ามผู้ขออนุมัติคำขอของตนเอง** (`approver_id ≠ ticket.requester_id`) → `422 SELF_APPROVAL_FORBIDDEN`
- ปฏิเสธขั้นใด → ticket ไป `cancelled` พร้อมเหตุผลจาก `comment` (บังคับ)
- ขณะมีขั้น `pending` → ticket อยู่ `pending_user` + `pending_reason='approval'` → **หยุดนับ SLA**

### 2.7 ข้อยกเว้น — เหตุความปลอดภัย 🆕

|---|---|
| `requester_id` | ผู้แจ้ง |
| `assignee_id` · `incident_commander_id` | ผู้รับผิดชอบ |
| ผู้ที่อยู่ใน `escalation_contact` ที่ `contact_key IN ('head_of_it','ceo','dpo')` | ระดับบริษัทนั้นหรือระดับกลุ่ม |
| `super_admin` | |

**`company_admin` และ `agent` คนอื่นในบริษัทเดียวกันไม่เห็น** — เป็นข้อยกเว้นเดียวในระบบที่ขอบเขตแคบกว่าบริษัท และต้องมีเทสต์เฉพาะใน `tests/api/test_security_incident_visibility.py`

| `P2` | สูง | **30 นาทีทำการ** | **8 ชั่วโมงทำการ** = 480 นาที | `business_hours` | ทุก 4 ชั่วโมงทำการ |

| `P4` | ต่ำ | **4 ชั่วโมงทำการ** = 240 นาที | **5 วันทำการ** = 2,700 นาที | `business_hours` | เมื่อสถานะเปลี่ยน |

> **เป้าหมายรวม:** อย่างน้อย **ร้อยละ 95** ของ Ticket ในแต่ละเดือนต้องแก้ไขได้ภายในเวลาที่กำหนด (SLA 5.1)
> **การเตือนล่วงหน้าที่ 75%** เป็นกลไกภายในที่ทีมเพิ่มเอง ไม่ได้มาจากเอกสารควบคุม — คงไว้ได้เพราะไม่ขัดกัน
> **คำขอบริการไม่ใช้ตารางนี้วัด resolution** — ใช้เป้าหมายรายรายการจาก `service_catalog_item` (SLA 5.3) แต่ **`response_due_at` ยังใช้ตารางนี้เสมอ**

### 3.3 นิยามที่ใช้วัด

| คำ | นิยาม |
|---|---|
| เวลาตอบรับ | จากเริ่มนับถึง**คอมเมนต์สาธารณะครั้งแรกจาก agent** (`first_response_at`) — **การ assign ไม่นับ** |
| เวลาแก้ไข | จาก `sla_clock_started_at` ถึง `resolved_at` หักเวลาที่หยุดนับ |
| **Workaround** | เมื่อ agent บันทึกทางเลี่ยงที่ทำให้ผู้ใช้ทำงานต่อได้ (`workaround_at`) → **หยุดนับเวลาแก้ไขของ Incident ทันที** งานแก้ถาวรติดตามต่อในรูปแบบ **Problem** |

## 4. การหยุดนับเวลาและ Escalation

### 4.1 การหยุดนับเวลา (SLA 5.4 และ 9)

| กฎ | รายละเอียด |
|---|---|
| สถานะที่หยุดนับ | `pending_user` โดยแยก **`pending_reason`** 3 แบบ: `user` (รอข้อมูล/การยืนยันจากผู้แจ้ง) · `vendor` (รออะไหล่/ผู้ให้บริการภายนอก **ที่แจ้งผู้รับบริการแล้ว**) · `approval` (รอการอนุมัติ) |
| สถานะที่ยังนับต่อ | `new`, `assigned`, `in_progress` |
| **Workaround** | `workaround_at` → **หยุดนับ resolution ของ Incident ทันที** และ**บังคับเปิด `problem`** มิฉะนั้น `409 WORKAROUND_REQUIRES_PROBLEM` |
| เงื่อนไขการเข้า `pending_user` | `user` ต้องมีคอมเมนต์สาธารณะระบุสิ่งที่รอ · **`vendor` ต้องมีคอมเมนต์สาธารณะแจ้งผู้รับบริการก่อน จึงตั้ง `pending_notified_at` ได้** · `approval` ระบบตั้งอัตโนมัติเมื่อมี `approval_request` ค้าง |
| การกลับมานับต่อ | อัตโนมัติเมื่อผู้แจ้งคอมเมนต์ / อนุมัติครบ / agent เปลี่ยนสถานะเอง |
| การบันทึก | บวกเวลาที่หยุด (นาทีทำการ) เข้า `pending_duration_minutes` และเลื่อน `resolution_due_at` ออกไปเท่ากัน |
| **response SLA** | **ไม่หยุด** — วัดถึงการตอบครั้งแรกเท่านั้น |
| การป้องกันการใช้ผิด | เข้า `pending_user` เกิน 3 ครั้ง → ทำเครื่องหมายในรายงานให้ company_admin ตรวจสอบ (นับจาก `ticket_status_history`) |
| **ผู้แจ้งไม่ตอบกลับ** | ระบบส่ง**ติดตาม 2 ครั้ง** (ห่างกัน 1 วันทำการ) → ยังไม่ตอบภายใน **3 วันทำการ** หลังครั้งที่ 2 → **ปิด Ticket** พร้อมแจ้งให้ทราบ และเปิดใหม่ได้ · ใช้ `followup_count`, `last_followup_at` |
| ข้อยกเว้นที่ไม่ถือเป็นการผิด SLA (SLA ข้อ 9) | `planned_maintenance` · `force_majeure` · `vendor_delay` · `user_installed` · `waiting_requester` · `agreed_special_terms` → บันทึกที่ `sla_exclusion_code` + `sla_exclusion_note` |

> **กฎที่ยกเลิกจากเวอร์ชัน 1.0:** "`pending_user` เกิน 5 วันทำการ → `resolved` อัตโนมัติ" — ขัดเอกสารเพราะไม่มีการติดตามก่อนปิด (G-09)

### 4.2 การประเมิน SLA Breach

งาน `scan_sla` ทำงานทุก 5 นาที ประเมินทุก ticket ที่สถานะไม่ใช่ `resolved`/`closed`/`cancelled`

| เงื่อนไข | ผลลัพธ์ |
|---|---|
| `first_response_at IS NULL` และ `now() > response_due_at` | `is_response_breached = true` + แจ้ง `sla_breached` |
| `now() > resolution_due_at` และยังไม่ `resolved` | `is_resolution_breached = true` + แจ้ง `sla_breached` |
| ใช้เวลาไป ≥ 75% และยังไม่เคยแจ้ง | แจ้ง `sla_warning` + ตั้ง `escalation_notified_at` (ครั้งเดียวต่อ ticket) |
| สถานะ `pending_user` (ทุก reason) | **ข้าม** ไม่ประเมิน ไม่แจ้งเตือน |
| มี `workaround_at` แล้ว (Incident) | **ข้ามการประเมิน resolution** — นาฬิกาหยุดที่ `workaround_at` |
| มี `sla_exclusion_code` | **ข้าม** ไม่ตั้งธง breach และไม่นับเข้า KPI |
| **priority = `P1`** | **ประเมินทุก 5 นาทีตลอด 24 ชม.** รวมนอกเวลาทำการและวันหยุด |

**สถานะ SLA ที่แสดงบน UI** (คำนวณตอนอ่าน ไม่เก็บในฐานข้อมูล)

| ค่า | เงื่อนไข |
|---|---|
| `on_track` | เหลือเวลา > 20% |
| `at_risk` | เหลือเวลา ≤ 20% |
| `breached` | เกิน `resolution_due_at` |
| `paused` | สถานะ `pending_user` |

> **การเปลี่ยน priority ระหว่างทาง (SLA 5.4):** *"การปรับลด/เพิ่มระดับความสำคัญระหว่างทาง ให้นับเวลาตามระดับใหม่**ตั้งแต่เวลาที่ปรับ**"* → คำนวณ due ใหม่จาก **`priority_changed_at`** ไม่ใช่จาก `created_at` และต้องบันทึกเหตุผลใน `ticket_status_history` (บังคับ)

## 6. เกณฑ์การจัดระดับความสำคัญ

> **Service Desk เป็นผู้กำหนดระดับเบื้องต้น** และผู้รับบริการ**ขอทบทวนระดับได้โดยระบุเหตุผลทางธุรกิจ** (SLA ข้อ 4 / SOP 5.1)

### 6.1 Priority Matrix = ผลกระทบ × ความเร่งด่วน

| ผลกระทบ ↓ / ความเร่งด่วน → | เร่งด่วนมาก (`high`) | เร่งด่วนปานกลาง (`medium`) | ไม่เร่งด่วน (`low`) |
|---|---|---|---|
| **ทั้งองค์กร / ระบบ Critical** (`org_wide`) | **P1** | **P2** | **P3** |
| **ทั้งแผนก / หลายคน** (`department`) | **P2** | **P3** | **P3** |
| **รายบุคคล** (`individual`) | **P3** | **P3** | **P4** |

**สีบน UI:** `P1` แดง · `P2` ส้ม · `P3` เหลืองเข้ม · `P4` เขียว (ค่าจริงดู `21-ui-ux-design.md` §4.2)

### 6.2 นิยามตามเอกสารจริง

| ระดับ | นิยาม | ตัวอย่าง |
|---|---|---|
| **P1** | ระบบ Critical หยุดให้บริการทั้งองค์กร **ไม่มีทางเลี่ยง** | ERP ล่ม · เครือข่ายทั้งสำนักงานใช้ไม่ได้ · โจมตีทางไซเบอร์ · ข้อมูลรั่วไหล · WMS/TMS ล่มจนรับ-จ่ายสินค้าไม่ได้ · e-Tax ใช้ไม่ได้วันปิดยอด |
| **P2** | ระบบสำคัญใช้ไม่ได้ทั้งแผนก **หรือระบบ Critical ที่มีทางเลี่ยงชั่วคราว** | โมดูลหลัก ERP ช้าผิดปกติ · อีเมลทั้งแผนกใช้ไม่ได้ · เน็ตไซต์งานล่ม · License โปรแกรมออกแบบหมดอายุทั้งทีม |
| **P3** | ผู้ใช้รายบุคคลทำงานไม่ได้หรือไม่สะดวก | เครื่องพิมพ์ตัวใดตัวหนึ่งเสีย · Wi-Fi อ่อนบางจุด · คอมพิวเตอร์ช้า · CCTV ไซต์งาน 1 ตัวภาพไม่ขึ้น |
| **P4** | **คำขอบริการทั่วไป**หรือคำปรึกษาที่ไม่กระทบงานเร่งด่วน | ขอสิทธิ์เข้าถึง · ติดตั้งโปรแกรม · ขอเปลี่ยนเมาส์ · สอบถามวิธีใช้งาน |

> ⚠️ **P4 ไม่ได้ใช้ resolution 5 วันทำการเสมอไป** — คำขอบริการมีเป้าหมายรายรายการตาม SLA 5.3 (รีเซ็ตรหัสผ่าน 30 นาทีทำการ · ขอสิทธิ์ 1 วันทำการ · ติดตั้งซอฟต์แวร์ 2 วันทำการ · จัดหาอุปกรณ์ 10 วันทำการ) จึงต้องแยก `ticket_type` และใช้ `service_catalog_item`

### 6.3 กติกาการกำหนดและปรับระดับ

| กติกา | รายละเอียด | ที่มา |
|---|---|---|
| **ระบบคำนวณให้อัตโนมัติ** | จาก `impact × urgency` · `POST /tickets` ที่ส่ง `priority` มาโดยตรงตอบ `422` | SLA 4 |
| ผู้แจ้งเลือกอะไรได้ | ตอบคำถาม "ปัญหานี้กระทบใครบ้าง" และ "เร่งด่วนแค่ไหน" — **ไม่ได้เลือกระดับโดยตรง** | SLA 4 |
| **ผู้รับบริการขอทบทวนได้** | `POST /tickets/{id}/priority-review` พร้อม**เหตุผลทางธุรกิจ** (บังคับ) → agent อนุมัติ/ปฏิเสธพร้อมเหตุผล | SLA 4 (ES-08) |
| agent ทบทวนได้เสมอ | ต้องระบุเหตุผลทุกครั้ง บันทึกใน `ticket_status_history` | SLA 5.4 |
| **นาฬิกาเมื่อเปลี่ยนระดับ** | **นับตามระดับใหม่ตั้งแต่ `priority_changed_at`** ไม่ใช่จาก `created_at` | SLA 5.4 |
| ค่าเริ่มต้นจากหมวดหมู่ | ระบบเติม `default_impact`/`default_urgency` ของหมวดหมู่เป็นค่าตั้งต้น | ทีมเพิ่มเอง |
| การปรับขึ้นเป็น `P1` | ตั้ง `is_major_incident` + แจ้ง `head_of_it` และ On-call ทันที (ES-01) | SLA 6.2 / SOP-02 |
| การปรับลง | ทำได้เฉพาะ `agent` ขึ้นไป และต้องแจ้งผู้แจ้งผ่านคอมเมนต์สาธารณะ | ทีมเพิ่มเอง |
| ตรวจสอบย้อนหลัง | รายงานรายเดือนแสดง ticket ที่มีการเปลี่ยนระดับ เพื่อดูว่าเกณฑ์ใช้ได้จริงหรือไม่ | ทีมเพิ่มเอง |
