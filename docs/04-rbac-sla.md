## 1. นิยาม Role และขอบเขตข้อมูล

| role | ชื่อไทย | ขอบเขตข้อมูล (row-level) | ตัวอย่างผู้ถือ role |
|---|---|---|---|
| `end_user` | ผู้แจ้ง | เฉพาะ ticket ที่ตนเป็น `requester_id` หรือ `created_by` | พนักงานทั่วไป, คนขับรถ, ช่างหน้างาน |
| `agent` | เจ้าหน้าที่ support | ทุก ticket ในบริษัทที่อยู่ใน `scoped_company_ids` | ทีม IT ส่วนกลาง, IT ประจำบริษัท |
| `company_admin` | ผู้ดูแลระดับบริษัท | ทุก ticket + ผู้ใช้ + การตั้งค่าย่อย ในบริษัทที่อยู่ใน `scoped_company_ids` | หัวหน้า IT ของแต่ละบริษัท |
| `manager_viewer` | ผู้บริหาร (อ่านอย่างเดียว) | อ่าน ticket/รายงาน ในบริษัทที่อยู่ใน `scoped_company_ids` | ผู้จัดการฝ่าย, ผู้บริหารกลุ่ม |
| `super_admin` | ผู้ดูแลระบบ | ทุกบริษัท ไม่มีข้อจำกัด | หัวหน้า IT กลุ่ม AIDC (แนะนำไม่เกิน 2 บัญชี) |

### 1.1 กติกาสำคัญ
1. ผู้ใช้ทุกคนมี `end_user` เป็นพื้นฐานเสมอ (แจ้งปัญหาของตนเองได้) และเพิ่ม role อื่นได้
2. เมื่อมีหลาย role → สิทธิ์คือ **ผลรวม (union)** ของ permission และ **ผลรวมของขอบเขตบริษัท**
3. `super_admin` ทับทุกกฎ — จึงต้องจำกัดจำนวนบัญชีและมี audit log ทุกการกระทำ
4. `manager_viewer` เป็น role อ่านอย่างเดียวโดยเจตนา: **การมี role อื่นควบคู่ไม่ทำให้เป็น read-only** — ถ้าต้องการให้ผู้บริหารแก้ไขไม่ได้ ต้องมอบเฉพาะ `end_user` + `manager_viewer`
5. ขอบเขตบริษัทมาจาก `user_role_scope`; ถ้าไม่กำหนด → ใช้ `app_user.company_id`
6. **ทุกการตรวจสิทธิ์ต้องทำที่ backend** การซ่อนปุ่มใน UI เป็นเพียงประสบการณ์ผู้ใช้ ไม่ใช่มาตรการความปลอดภัย

## 3. ตาราง SLA

> **ทั้งหัวข้อนี้อ้างอิง AIDC-IT-SLA-001 v1.1 หัวข้อ 1.4, 3.1, 5.1 และ 5.4** — ตัวเลขทุกตัวมาจากเอกสารควบคุม ไม่ใช่สมมติฐานของทีมอีกต่อไป ตาราง seed ที่พร้อมใส่ฐานข้อมูลอยู่ใน [`05-sla-policy-alignment.md`](./05-sla-policy-alignment.md) หัวข้อ 3

### 3.1 ฐานการคำนวณ

| ประเด็น | ค่าที่ใช้ | ที่มา / หมายเหตุ |
|---|---|---|
| เวลาทำการ | **จันทร์–ศุกร์ 08:30–17:30 น.** ยกเว้นวันหยุดบริษัท | SLA 1.4 และ 3.1 — **เสาร์ไม่ใช่วันทำการ** |
| ชั่วโมงทำการต่อวัน | 9 ชั่วโมง = **540 นาที** | ไม่หักพักกลางวัน (เอกสารไม่ได้กำหนดให้หัก) |
| 1 วันทำการ | **= 540 นาทีทำการ** | ใช้ตีความคำว่า "วันทำการ" ทุกแห่งในเอกสาร (ปิดประเด็น S-02 ของ Backend) |
| เสาร์–อาทิตย์ | ไม่นับเวลา | |
| วันหยุดบริษัท | ไม่นับเวลา (ตาราง `holiday`) | **[ต้องยืนยันกับ PM]** ต้องขอปฏิทินวันหยุดฉบับทางการ — เอกสาร SLA ไม่ได้แนบมา |
| นาฬิกาเริ่มเดิน | เวลาที่สร้าง ticket — ถ้าสร้างนอกเวลาทำการ เริ่มนับที่เวลาเปิดทำการถัดไป | ยกเว้น P1 ที่นับทันทีตลอด 24 ชม. และคำขอบริการที่มีเงื่อนไขเริ่มนับเฉพาะ (ดู `05-…` หัวข้อ 7) |
| **โหมดนาฬิกา** | **P1 นับต่อเนื่อง 24×7** (มีทีม On-call) · **P2–P4 นับเฉพาะนาทีทำการ** | SLA 5.4 — เก็บใน `sla_target.clock_mode` |
| ปิดปรับปรุงตามแผน | เสาร์ 20:00–24:00 แจ้งล่วงหน้า ≥ 3 วันทำการ — ไม่นับเป็น Downtime | SLA 3.1, 9 |

### 3.2 ตาราง SLA มาตรฐาน (ตาม AIDC-IT-SLA-001 v1.1 หัวข้อ 5.1)

| priority | ชื่อไทย | เวลาตอบรับ (response) | เวลาแก้ไข (resolution) | โหมดนาฬิกา | การรายงานสถานะ |
|---|---|---|---|---|---|
| `P1` | วิกฤต | **15 นาที** (24×7) | **4 ชั่วโมง** = 240 นาที นับต่อเนื่อง | `calendar_24x7` | **ทุก 1 ชั่วโมง** จนกว่าจะแก้ไขเสร็จ |
| `P2` | สูง | **30 นาทีทำการ** | **8 ชั่วโมงทำการ** = 480 นาที | `business_hours` | ทุก 4 ชั่วโมงทำการ |
| `P3` | ปานกลาง | **2 ชั่วโมงทำการ** = 120 นาที | **2 วันทำการ** = 1,080 นาที | `business_hours` | เมื่อสถานะเปลี่ยน |
| `P4` | ต่ำ | **4 ชั่วโมงทำการ** = 240 นาที | **5 วันทำการ** = 2,700 นาที | `business_hours` | เมื่อสถานะเปลี่ยน |

> **เป้าหมายรวมตามเอกสาร:** อย่างน้อย **ร้อยละ 95** ของ Ticket ทั้งหมดในแต่ละเดือนต้องแก้ไขได้ภายในเวลาที่กำหนด (SLA 5.1)
> **การเตือนล่วงหน้าที่ 75%** (`sla_target.escalation_percent`) เป็นกลไกภายในของระบบที่ทีมเพิ่มเอง ไม่ได้มาจากเอกสารควบคุม — คงไว้ได้เพราะไม่ขัดกัน
> **คำขอบริการ (Service Request)** ไม่ใช้ตารางนี้ในการวัด resolution — ใช้เป้าหมายรายรายการตาม SLA 5.3 (เช่น รีเซ็ตรหัสผ่าน 30 นาทีทำการ) ดู `05-…` หัวข้อ 7

**นิยามที่ใช้วัด**

| คำ | นิยาม |
|---|---|
| เวลาตอบรับ (response) | เวลาจากสร้าง ticket จนถึง**คอมเมนต์สาธารณะครั้งแรกจาก agent** (`first_response_at`) — การ assign เฉย ๆ **ไม่นับ** ว่าตอบรับแล้ว |
| เวลาแก้ไข (resolution) | เวลาจากเริ่มนับ (`sla_clock_started_at` หรือ `created_at`) จนถึงสถานะ `resolved` (`resolved_at`) หักด้วยเวลาที่หยุดนับตามหัวข้อ 4.1 |
| **Workaround** | เมื่อ agent บันทึกทางเลี่ยงชั่วคราวที่ทำให้ผู้ใช้ทำงานต่อได้ (`workaround_at`) → **หยุดนับเวลาแก้ไขของ Incident** งานแก้ถาวรติดตามต่อในรูปแบบ **Problem** (SLA 5.4) |
| SLA met | `first_response_at <= response_due_at` และ/หรือ `resolved_at <= resolution_due_at` |
| ข้อยกเว้น | ticket ที่มี `sla_exclusion_code` (ตาม SLA ข้อ 9) ไม่ถูกตั้งธง breach และถูกตัดออกจากตัวหารของ KPI |

| 4 | จ. 09:00 | `P3` | 1,080 นาทีทำการ | **พ. 09:00** | จ. 510 (09:00–17:30) + อ. 540 + พ. 30 นาที |

> - `clock_start` = `priority_changed_at` ถ้ามีการเปลี่ยน priority · มิฉะนั้น `sla_clock_started_at` · มิฉะนั้น `created_at`

## 4. กฎการหยุดนับเวลาและ Escalation

### 4.1 การหยุดนับเวลา (SLA pause)

> อ้างอิง **AIDC-IT-SLA-001 v1.1 หัวข้อ 5.4 และ 9**

| กฎ | รายละเอียด |
|---|---|
| สถานะที่หยุดนับ | `pending_user` โดยแยก **`pending_reason`** 3 แบบตามเอกสาร: `user` (รอข้อมูล/การยืนยันจากผู้แจ้ง) · `vendor` (รออะไหล่/ผู้ให้บริการภายนอก **ที่แจ้งผู้รับบริการแล้ว**) · `approval` (รอการอนุมัติจากฝั่งผู้รับบริการ) |
| สถานะที่ยังนับต่อ | `new`, `assigned`, `in_progress` |
| สถานะที่หยุดนับถาวร | `resolved`, `closed`, `cancelled` |
| **Workaround** | บันทึก `workaround_at` → **หยุดนับ resolution ของ Incident ทันที** และต้องเปิด `problem` เพื่อติดตามการแก้ถาวร (SLA 5.4) |
| เงื่อนไขการเข้า `pending_user` | `reason='user'` ต้องมีคอมเมนต์สาธารณะระบุสิ่งที่รอ (บังคับ) · `reason='vendor'` ต้องมีคอมเมนต์สาธารณะแจ้งผู้รับบริการก่อน จึงตั้ง `pending_notified_at` ได้ · `reason='approval'` ระบบตั้งให้อัตโนมัติเมื่อมี `approval_request` ค้าง |
| การกลับมานับต่อ | อัตโนมัติเมื่อผู้แจ้งคอมเมนต์ / อนุมัติครบ / agent เปลี่ยนสถานะเอง |
| การบันทึก | บวกเวลาที่หยุด (นาทีทำการ) เข้า `pending_duration_minutes` และเลื่อน `resolution_due_at` ออกไปเท่ากัน |
| **response SLA** | **ไม่หยุด** — วัดถึงการตอบครั้งแรกเท่านั้น จึงไม่เกี่ยวกับ `pending_user` |
| การป้องกันการใช้ผิด | ถ้า ticket เข้า `pending_user` เกิน 3 ครั้ง ระบบทำเครื่องหมายในรายงานให้ company_admin ตรวจสอบ |
| **ผู้แจ้งไม่ตอบกลับ** | ระบบส่ง**ติดตาม 2 ครั้ง** (ห่างกัน 1 วันทำการ) → ถ้ายังไม่ตอบภายใน **3 วันทำการ** หลังการติดตามครั้งที่ 2 → ปิด Ticket พร้อมแจ้งให้ทราบ และผู้แจ้งเปิดใหม่ได้เมื่อพร้อม (SLA 5.4 / SOP-01 ข้อ 9) — ใช้ `followup_count`, `last_followup_at`<br>*(ยกเลิกกฎเดิม "pending_user เกิน 5 วันทำการ → `resolved` อัตโนมัติ" ซึ่งขัดกับเอกสารเพราะไม่มีการติดตามก่อนปิด)* |
| ข้อยกเว้นที่ไม่ถือเป็นการผิด SLA (SLA ข้อ 9) | ปิดปรับปรุงตามแผน · เหตุสุดวิสัย · ความล่าช้าจากผู้ให้บริการภายนอกที่ติดตามและสื่อสารแล้ว · ปัญหาจากอุปกรณ์/ซอฟต์แวร์ที่ผู้ใช้ติดตั้งเอง · เวลารอผู้แจ้ง/การอนุมัติ · คำขอเร่งด่วนพิเศษที่ตกลงเงื่อนไขเวลาใหม่ร่วมกันแล้ว → บันทึกที่ `ticket.sla_exclusion_code` + `sla_exclusion_note` |

### 4.2 การคำนวณ SLA Breach

งาน `scan_sla` ทำงานทุก 5 นาที และประเมินทุก ticket ที่สถานะไม่ใช่ `resolved` / `closed` / `cancelled`

| เงื่อนไข | ผลลัพธ์ |
|---|---|
| `first_response_at IS NULL` และ `now() > response_due_at` | `is_response_breached = true` + แจ้งเตือน `sla_breached` |
| `now() > resolution_due_at` และยังไม่ `resolved` | `is_resolution_breached = true` + แจ้งเตือน `sla_breached` |
| ใช้เวลาไปแล้ว ≥ `escalation_percent` (75%) และยังไม่เคยแจ้ง | แจ้งเตือน `sla_warning` + ตั้ง `escalation_notified_at` (แจ้งครั้งเดียวต่อ ticket) |
| สถานะ `pending_user` (ทุก `pending_reason`) | ข้าม ไม่ประเมิน ไม่แจ้งเตือน |
| มี `workaround_at` แล้ว (Incident) | ข้ามการประเมิน resolution — นาฬิกาหยุดที่ `workaround_at` |
| มี `sla_exclusion_code` | ข้าม ไม่ตั้งธง breach และไม่นับเข้า KPI |
| **priority = `P1`** | **ประเมินทุก 5 นาทีตลอด 24 ชม.** รวมนอกเวลาทำการและวันหยุด (นาฬิกา `calendar_24x7`) |

**สถานะ SLA ที่แสดงบน UI** (คำนวณตอนอ่านข้อมูล ไม่เก็บในฐานข้อมูล)

| ค่า | เงื่อนไข | สีที่แสดง |
|---|---|---|
| `on_track` | เหลือเวลา > 20% | เขียว |
| `at_risk` | เหลือเวลา ≤ 20% | ส้ม |
| `breached` | เกิน `resolution_due_at` | แดง |
| `paused` | สถานะ `pending_user` | เทา |

> **การเปลี่ยน priority ระหว่างทาง (แก้ตาม SLA 5.4):** *"การปรับลด/เพิ่มระดับความสำคัญระหว่างทาง ให้นับเวลาตามระดับใหม่**ตั้งแต่เวลาที่ปรับ**"* → คำนวณ `response_due_at` / `resolution_due_at` ใหม่จาก **`priority_changed_at` (= เวลาที่ปรับ)** ด้วย target ของ priority ใหม่ — **ไม่ใช่จาก `created_at` เดิม** และต้องบันทึกเหตุผลใน `ticket_status_history` (บังคับ)

### 4.3 กฎ Escalation

> อ้างอิง **AIDC-IT-SLA-001 v1.1 หัวข้อ 6.1 (Functional) และ 6.2 (Hierarchical)** — รายละเอียดเต็มพร้อมตาราง `escalation_contact` / `sla_escalation_rule` อยู่ใน [`05-sla-policy-alignment.md`](./05-sla-policy-alignment.md) หัวข้อ 5

**Functional Escalation — ระดับชั้นทีมสนับสนุน** (`ticket.support_tier`)

| ลำดับ | ผู้รับผิดชอบ | เงื่อนไขการยกระดับตามเอกสาร | การกระทำของระบบ |
|---|---|---|---|
| Tier 1 | เจ้าหน้าที่ Service Desk | รับงานทั้งหมดเป็นด่านแรก | `support_tier = 1` เป็นค่าเริ่มต้นทุก ticket |
| Tier 2 | System / Network Admin | **Tier 1 แก้ไม่ได้ภายใน 2 ชั่วโมงทำการ** หรือเป็นปัญหาเชิงเทคนิคลึก | เมื่อครบ 2 ชม.ทำการ → ตั้งธง "ต้องยกระดับ Tier 2" + แจ้งเตือน (agent ต้องยืนยันพร้อมสรุปสิ่งที่ตรวจสอบแล้ว ตาม SOP-01 ข้อ 5 — ระบบไม่เปลี่ยน tier ให้เอง) |
| Tier 3 | ผู้เชี่ยวชาญเฉพาะทาง / Vendor | Tier 2 แก้ไม่ได้ หรืออยู่ในความรับผิดชอบของผู้ผลิต/ผู้ให้บริการภายนอก | ตั้ง `support_tier = 3` + บังคับกรอก `vendor_ref` + เปิดให้ใช้ `pending_reason='vendor'` |

**Hierarchical Escalation — ยกระดับสู่ผู้บริหาร** (ผู้รับแจ้งมาจากตาราง `escalation_contact`)

| ทริกเกอร์ | เงื่อนไขตามเอกสาร | การกระทำของระบบ | ผู้รับแจ้ง |
|---|---|---|---|
| ES-01 · เหตุ P1 | **P1 ทุกกรณี ทันที** | แจ้งเตือนทันทีแม้นอกเวลาทำการ + ตั้ง `is_major_incident` | `head_of_it` + agent ในขอบเขต + ทีม On-call |
| ES-02 · P1 ยืดเยื้อ | **P1 เกิน 4 ชั่วโมง (ปฏิทิน) ยังไม่คืนบริการ** | ยกระดับสู่ผู้บริหาร | `ceo` + `head_of_it` |
| ES-03 · เหตุความปลอดภัย | เหตุการณ์ความปลอดภัย / ข้อมูลรั่วไหล / กระทบลูกค้าภายนอก | แจ้งภายใน 30 นาที (SOP-10) + เริ่มนาฬิกา 72 ชม. แจ้งหน่วยงานกำกับ + จำกัดการมองเห็น ticket | `head_of_it` + `ceo` + `dpo` |
| ES-04 · Tier 1 เกิน 2 ชม.ทำการ | ดูตาราง Functional ข้างบน | ตั้งธง + แจ้งเตือน | `tier2_group` + ผู้รับผิดชอบ + `company_admin` |
| ES-06 · เกิน SLA | **Ticket ใดใช้เวลาเกิน SLA แล้ว** (response หรือ resolution) | แจ้งทันทีเมื่อ `scan_sla` ตั้งธง breach (ซ้ำได้วันละครั้ง) | `head_of_it` + ผู้รับผิดชอบ + `company_admin` |
| ES-07 · ผู้รับบริการขอทบทวน | ผู้รับบริการร้องขอทบทวนการจัดการ | สร้าง flag + แจ้งเตือน — ระบบต้องสื่อสารว่า **"ไม่ถือเป็นการร้องเรียน แต่เป็นกลไกปกติของการบริหารงานบริการ"** | `head_of_it` |
| ES-09 · รอบรายงานสถานะ | P1 ทุก 1 ชม. · P2 ทุก 4 ชม.ทำการ (SLA 5.1) | เตือนผู้รับผิดชอบเมื่อถึง `next_status_report_due_at` | ผู้รับผิดชอบ (+ `incident_manager` สำหรับ P1) |
| ES-10 · RCA ค้าง | P1 ปิดแล้วเกิน **5 วันทำการ** ยังไม่ส่ง RCA (SLA 7.2) | เตือน + ขึ้นในรายงานรายเดือน | เจ้าของ Problem + `head_of_it` |
| ES-11 · P1 ซ้ำสาเหตุเดิม | **P1 จากสาเหตุเดิมซ้ำภายใน 90 วัน** (SLA 7.3) | ตั้งธง "ต้องทบทวน RCA เดิมทันที" + นับเข้า KPI Repeat Incident | `head_of_it` + `ceo` |
| ES-12 · เตือนล่วงหน้า *(ส่วนขยายของทีม)* | ใช้เวลาไป 75% ของ resolution target | แจ้งครั้งเดียวต่อ ticket | ผู้รับผิดชอบ |

**กติกากันการรบกวนเกินจำเป็น**
- แจ้ง **ครั้งเดียวต่อ ticket ต่อกฎ** ยกเว้น ES-02 และ ES-09 (P1) ที่แจ้งซ้ำทุกชั่วโมง และ ES-06 ที่แจ้งซ้ำได้วันละครั้ง
- **ไม่ส่ง escalation นอกเวลาทำการ ยกเว้น `P1` และ ES-03** — สอดคล้องกับ SLA 3.1 ที่ On-call ครอบคลุมเฉพาะ P1
- ระงับการแจ้งเตือนทั้งหมดสำหรับ ticket ที่อยู่สถานะ `pending_user` ทุก `pending_reason`

## 5. รายงานที่ใช้วัดผล SLA

### 5.1 KPI ตามเอกสารควบคุม (AIDC-IT-SLA-001 v1.1 หัวข้อ 7.1) — **เป้าหมายบังคับ ไม่ใช่ข้อเสนอ**

| ตัวชี้วัด | เป้าหมาย | ความถี่ | สูตรคำนวณโดยย่อ |
|---|---|---|---|
| SLA Compliance | **≥ 95%** | รายเดือน | ticket ที่ปิดในเดือนและแก้ทันเวลา ÷ ticket ที่ปิดทั้งหมดในเดือน (ตัดข้อยกเว้นออกจากตัวหาร) |
| First Response Time (FRT) | **≤ 30 นาที** | รายเดือน | `AVG(created_at → first_response_at)` |
| First Contact Resolution (FCR) | **≥ 70%** | รายเดือน | incident ที่จบที่ Tier 1 ครั้งเดียว ÷ incident ที่ปิดทั้งหมด |
| CSAT | **≥ 4.2 / 5.0** | รายไตรมาส | `AVG(satisfaction_score)` **พร้อมรายงาน Response Rate ควบคู่เสมอ** (SLA ภาคผนวก ก.3) |
| Aged Backlog | **≤ 5% ของทั้งหมด** | **รายสัปดาห์** | ticket ที่ยังเปิดและเกิน `resolution_due_at` ÷ ticket ที่ยังเปิดทั้งหมด |
| Uptime ระบบ Critical | **≥ 99.9% ต่อเดือน** | รายเดือน | `[(เวลาที่ตกลงให้บริการ − downtime ไม่ได้วางแผน) ÷ เวลาที่ตกลงให้บริการ] × 100` |
| Repeat Incident | **≤ 10%** | รายไตรมาส | incident ที่ซ้ำสาเหตุเดิมภายใน 90 วัน ÷ incident ที่ปิดทั้งหมด |

> สูตรเต็ม ข้อมูลที่ต้องเก็บเพิ่ม และตารางใหม่ที่ต้องสร้าง (`service`, `service_outage`, `problem`) ดู [`05-sla-policy-alignment.md`](./05-sla-policy-alignment.md) หัวข้อ 6 และ 8
> **เป้าหมายความพร้อมใช้งานตาม Service Tier:** Critical ≥ 99.9% · High ≥ 99.5% · Standard ≥ 99.0% (SLA 5.2)

## 6. เกณฑ์การจัดระดับความสำคัญ (Priority P1–P4)

> อ้างอิง **AIDC-IT-SLA-001 v1.1 หัวข้อ 4** และ AIDC-IT-SOP-001 v1.1 หัวข้อ 5.1 — **Service Desk เป็นผู้กำหนดระดับเบื้องต้น** และผู้รับบริการ **ขอทบทวนระดับได้โดยระบุเหตุผลทางธุรกิจ**

### 6.1 Priority Matrix = ผลกระทบ (Impact) × ความเร่งด่วน (Urgency)

| ผลกระทบ ↓ / ความเร่งด่วน → | เร่งด่วนมาก | เร่งด่วนปานกลาง | ไม่เร่งด่วน |
|---|---|---|---|
| **ทั้งองค์กร / ระบบ Critical** | **P1 – Critical** | **P2 – High** | **P3 – Medium** |
| **ทั้งแผนก / หลายคน** | **P2 – High** | **P3 – Medium** | **P3 – Medium** |
| **รายบุคคล** | **P3 – Medium** | **P3 – Medium** | **P4 – Low** |

**ค่า enum ที่ระบบใช้:** `ticket.impact` = `org_wide` / `department` / `individual` · `ticket.urgency` = `high` / `medium` / `low` · `ticket.priority` = `P1` / `P2` / `P3` / `P4` (**ระบบคำนวณจากเมทริกซ์ให้อัตโนมัติ** agent ปรับได้พร้อมเหตุผลบังคับ)

**สีบน UI:** `P1` แดง · `P2` ส้ม · `P3` เหลือง · `P4` เขียว

### 6.2 นิยามตามเอกสารจริงและตัวอย่างรายบริษัท

> ตัวอย่างของบริษัทอื่นนอกจาก AIDC Tech เป็นการแมปตัวอย่างเดิมของทีมเข้ากับนิยาม P1–P4 — **[ต้องยืนยันกับ PM]** (ดู `05-sla-policy-alignment.md` หัวข้อ 2.3 และ 10)

#### `P1` — Critical (วิกฤต)
> **นิยามตามเอกสาร:** ระบบ Critical หยุดให้บริการทั้งองค์กร **ไม่มีทางเลี่ยง** เช่น ERP ล่ม เครือข่ายทั้งสำนักงานใช้ไม่ได้ เหตุโจมตีทางไซเบอร์ หรือข้อมูลรั่วไหล

| บริษัท | ตัวอย่างสถานการณ์จริง |
|---|---|
| AIDC HQ | ระบบไฟล์เซิร์ฟเวอร์กลางล่ม ทุกบริษัทเข้าเอกสารไม่ได้ / อีเมลทั้งองค์กรล่ม |
| AIDC Construction | ระบบรายงานหน้างานล่มในวันส่งงานตามสัญญา / ไฟล์แบบก่อสร้างโครงการหลักเสียหาย |
| COSI | ไฟล์โครงการที่กำลังส่งลูกค้าเสียหายและต้องกู้จาก backup ทันที |
| Heavy Machine | ระบบใบสั่งงานซ่อมล่ม ศูนย์บริการทั้งหมดรับงาน/เบิกอะไหล่ไม่ได้ |
| AIDC Tech | เซิร์ฟเวอร์ระบบหลักดับ / ตรวจพบ ransomware ในเครือข่าย |
| AIDC Trading | ระบบออกใบกำกับภาษี e-Tax ใช้ไม่ได้ในวันปิดยอด / ระบบใบสั่งขายล่ม |
| AIDC Logistic | ระบบ WMS หรือ TMS ล่ม รับ-จ่ายสินค้าและจัดรถไม่ได้ มีรถรอคิวหน้าคลัง |

#### `P2` — High (สูง)
> **นิยามตามเอกสาร:** ระบบสำคัญใช้ไม่ได้ทั้งแผนก **หรือระบบ Critical ที่มีทางเลี่ยงชั่วคราว** เช่น โมดูลหลักของ ERP ช้าผิดปกติ อีเมลทั้งแผนกใช้ไม่ได้

| บริษัท | ตัวอย่างสถานการณ์จริง |
|---|---|
| AIDC HQ | อินเทอร์เน็ตทั้งชั้นใช้ไม่ได้ / ผู้บริหารเข้าอีเมลไม่ได้ก่อนประชุม |
| AIDC Construction | เน็ต 4G ที่ไซต์งานใช้ไม่ได้ ส่งรายงานประจำวันไม่ได้ / plotter พิมพ์แบบไม่ออกก่อนประชุมหน้างาน |
| COSI | License โปรแกรมออกแบบหมดอายุ ทีมออกแบบทำงานไม่ได้ |
| Heavy Machine | แท็บเล็ตช่างบริการนอกสถานที่ใช้ไม่ได้ ปิดงานหน้าลูกค้าไม่ได้ / ระบบสต็อกอะไหล่ค้นไม่ได้ |
| AIDC Tech | ระบบภายในที่พัฒนาเองมีบั๊กกระทบผู้ใช้หลายคน |
| AIDC Trading | อีเมลติดต่อลูกค้าตีกลับ / ระบบเชื่อมต่อคู่ค้า (EDI) ส่งข้อมูลไม่ผ่าน |
| AIDC Logistic | เครื่องยิงบาร์โค้ดคลังใดคลังหนึ่งใช้ไม่ได้ / GPS ติดรถขาดการเชื่อมต่อทั้งชุด |

#### `P3` — Medium (ปานกลาง)
> **นิยามตามเอกสาร:** ผู้ใช้รายบุคคลทำงานไม่ได้หรือไม่สะดวก เช่น เครื่องคอมพิวเตอร์มีปัญหา เครื่องพิมพ์ใช้ไม่ได้ โปรแกรมสำนักงานผิดพลาด

| บริษัท | ตัวอย่างสถานการณ์จริง |
|---|---|
| ทุกบริษัท | เครื่องพิมพ์ตัวใดตัวหนึ่งเสีย (ยังใช้เครื่องอื่นได้) / Wi-Fi สัญญาณอ่อนบางจุด / ขอสิทธิ์เข้าถึงโฟลเดอร์ / คอมพิวเตอร์ทำงานช้า |
| AIDC Construction | กล้อง CCTV หน้าไซต์งาน 1 ตัวภาพไม่ขึ้น |
| Heavy Machine | ระบบติดตามพิกัดเครื่องจักรแสดงข้อมูลล่าช้า |
| AIDC Logistic | เครื่องพิมพ์ฉลากตัวสำรองใช้ไม่ได้ |

#### `P4` — Low (ต่ำ)
> **นิยามตามเอกสาร:** **คำขอบริการทั่วไป**หรือคำปรึกษาที่ไม่กระทบงานเร่งด่วน เช่น ขอสิทธิ์เข้าถึง ติดตั้งโปรแกรม ขออุปกรณ์ใหม่

| ตัวอย่าง (ทุกบริษัท) |
|---|
| ขอติดตั้งโปรแกรมเพิ่ม / ขอสิทธิ์เข้าถึงระบบ / ขอเปลี่ยนเมาส์ คีย์บอร์ด / สอบถามวิธีใช้งาน / ขออุปกรณ์สำหรับพนักงานใหม่ที่เริ่มงานสัปดาห์หน้า / ขอรายงานย้อนหลัง |

> **ข้อควรระวัง:** คำขอบริการที่ตกเป็น `P4` **ไม่ได้ใช้ resolution 5 วันทำการเสมอไป** — SLA 5.3 กำหนดเป้าหมายรายรายการไว้ต่างหาก (รีเซ็ตรหัสผ่าน 30 นาทีทำการ, ขอสิทธิ์ 1 วันทำการ, ติดตั้งซอฟต์แวร์ 2 วันทำการ, จัดหาอุปกรณ์ 10 วันทำการ) จึงต้องแยก `ticket_type = incident / service_request` — ดู `05-sla-policy-alignment.md` หัวข้อ 7

### 6.3 กติกาการกำหนดและปรับ priority

| กติกา | รายละเอียด | ที่มา |
|---|---|---|
| **Service Desk เป็นผู้กำหนดระดับเบื้องต้น** | ระบบคำนวณ `priority` จาก `impact × urgency` ให้อัตโนมัติ; agent ยืนยันหรือปรับได้ | SLA 4 |
| ผู้แจ้งเลือกอะไรได้ | ผู้แจ้งตอบคำถาม "ปัญหานี้กระทบใครบ้าง" และ "เร่งด่วนแค่ไหน" (impact/urgency) — **ไม่ได้เลือก `priority` โดยตรง** | SLA 4 |
| **ผู้รับบริการขอทบทวนระดับได้** | กดปุ่ม "ขอทบทวนระดับความสำคัญ" พร้อม **เหตุผลทางธุรกิจ** (บังคับ) → agent อนุมัติ/ปฏิเสธพร้อมเหตุผล (ES-08) | SLA 4 |
| agent ทบทวนได้เสมอ | ต้องระบุเหตุผลทุกครั้ง บันทึกใน `ticket_status_history` | SLA 5.4 |
| **นาฬิกาเมื่อเปลี่ยนระดับ** | **นับตามระดับใหม่ตั้งแต่เวลาที่ปรับ** (`priority_changed_at`) ไม่ใช่จาก `created_at` | SLA 5.4 |
| ค่าเริ่มต้นจากหมวดหมู่ | ระบบเติม `default_priority` ของหมวดหมู่ให้เป็นค่าตั้งต้นของ impact/urgency | ทีมเพิ่มเอง |
| การปรับขึ้นเป็น `P1` | ตั้ง `is_major_incident` + แจ้ง `head_of_it` และทีม On-call ทันที (ES-01) | SLA 6.2 / SOP-02 |
| การปรับลง | ทำได้เฉพาะ `agent` ขึ้นไป และต้องแจ้งผู้แจ้งผ่านคอมเมนต์สาธารณะ | ทีมเพิ่มเอง |
| ตรวจสอบย้อนหลัง | รายงานรายเดือนแสดง ticket ที่มีการเปลี่ยน priority เพื่อดูว่าเกณฑ์ใช้ได้จริงหรือไม่ | ทีมเพิ่มเอง |
